## 1. Что нового с v3

### 1.1. Автообновление на экране стены (foreground) — ЗАКРЫТО
Реализовано в `CameraWallViewModel`/`CameraWallScreen`/`SettingsScreen`:
- `startForegroundAutoRefresh(intervalSeconds)` — корутин-цикл
  `while (isActive) { delay(...); refreshAllCameras() }`, запускается в
  `LaunchedEffect(Unit)` на `CameraWallScreen`, останавливается в
  `DisposableEffect` при уходе с экрана.
- `applyRefreshInterval(seconds)` в `SettingsScreen` — единая точка изменения
  интервала, перезапускает foreground-цикл (если активен) и перепланирует
  фоновую задачу.

**Подтверждено логом**: после открытия экрана стены, через заданный интервал
обе тестовые камеры обновились, оба `captureFrame result: success`.

### 1.2. Автообновление в фоне (WorkManager) — ЗАПЛАНИРОВАНО, но выполнение не подтверждено
`init{}` в `CameraWallViewModel` теперь вызывает `scheduleBackgroundUpdates(...)`
при каждом создании ViewModel (то есть при каждом открытии приложения).
**Подтверждено логом постановки задачи**:
```
WM-GreedyScheduler   D  Cancelling work ID 083d03dd-...
WM-SystemJobScheduler D  Scheduling work ID 083d03dd-...  Job ID 2
```
Это значит: `CameraUpdateManager.scheduleCameraUpdates()` действительно
вызывается и WorkManager действительно принимает задачу в очередь
(`ExistingPeriodicWorkPolicy.UPDATE` пересоздаёт задачу при каждом запуске —
отсюда "Cancelling" + "Scheduling" в паре).

**Не подтверждено**: реальное выполнение `CameraUpdateWorker.doWork()` в фоне.
Интервал — минимум 15 минут (системное ограничение, см. v3 §2.2), а тестовый
прогон был короче. Нужно либо:
- подождать 15+ минут с закрытым приложением и проверить в логе появление
  `CameraUpdateWorker`/`RtspFrameCapture` записей без открытого экрана, либо
- вызвать `viewModel.triggerOneTimeUpdate()` (уже есть в коде, использует
  `OneTimeWorkRequestBuilder` без ограничения на 15 минут) для быстрой проверки,
  что сам `doWork()` реально обновляет БД и файлы, а не только логика
  планирования корректна.

### 1.3. Архитектурное замечание на будущее (не баг, но важно для этапа 5)
`refreshAllCameras()` — не `suspend`-функция, а обёртка над
`viewModelScope.launch { ... }`: вызывается и сразу возвращает управление, не
дожидаясь завершения обхода камер. Foreground-цикл эксплуатирует это осознанно
(таймер идёт по `delay()`, а не по факту завершения предыдущего обновления),
но при большом числе камер и/или коротком интервале это может привести к
пересекающимся параллельным обходам одних и тех же камер (новый вызов
`refreshAllCameras()` стартует раньше, чем закончился предыдущий). Сейчас (2
камеры, ~8.5 сек на обход) это не проявляется. Учесть при реализации этапа 5
(concurrency=2, retry≤2) — там всё равно нужен нормальный менеджер очереди
обновлений, который заодно решит и эту проблему (например, не запускать новый
обход, пока предыдущий не завершён, или ограничивать одновременные обходы
через `Mutex`/`Semaphore`).
