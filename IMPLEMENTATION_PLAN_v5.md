## 2. Этап B — отключение обновления камер

Поле `Camera.enabled` уже существует; `CameraUpdateWorker` уже пропускает
`enabled == false`. Недостающее:

### 2.1. Логика
1. `CameraWallViewModel`:
   - `refreshSweep()` и `refreshCamerasWithoutFrames()` — фильтровать
     `cameras.filter { it.enabled }` перед обходом (сейчас фильтр только в Worker).
   - Новый метод `setCameraEnabled(cameraId, enabled)`:
     `updateCameraUseCase(camera.copy(enabled = ...))` + `loadCameras()`.
2. Ручное обновление в детальном экране (`Refresh`) **остаётся доступным**
   и для отключённых камер — это и есть «просмотр только при явном открытии
   и нажатии кнопки».

### 2.2. UI
1. `CameraDetailScreen`: переключатель «Обновлять камеру» (Switch).
   Выключен → камера не участвует в автообновлении (foreground-цикл,
   быстрый старт, WorkManager).
2. `CameraWallScreen`: список делится на две группы:
   - сначала включённые (текущая сетка 2 колонки);
   - заголовок-разделитель «Отключенные»;
   - затем отключённые — те же карточки, но визуально приглушённые
     (сниженная яркость/бейдж), в конце списка.
   Реализация: один `LazyVerticalGrid`, `items()` по двум подспискам с
   `item { SectionHeader }` между ними. Сортировка внутри групп — текущая
   (`sortOrder ASC, name ASC`).
3. Опционально: быстрые действия «Включить/Выключить» долгим нажатием на
   карточку — только если нужно, в минимум не входит.

### 2.3. Проверка
- Unit: фильтр в sweep (логика выносится в тестируемую функцию).
- Ручная: выключить камеру → убедиться, что в логе обхода она skipped,
  карточка ушла в «Отключенные», ручное Refresh в деталях работает.

## 3. Этап A — добавление камеры по QR-коду

### 3.1. Формат QR (решение нужно подтвердить)
Предлагаю поддерживать два варианта содержимого:
1. Просто строка `rtsp://...` — подставляется в поле URL, имя вводится вручную.
2. JSON: `{"name": "...", "rtsp": "rtsp://..."}` — заполняются оба поля.
Всё остальное — ошибка «QR не распознан».

### 3.2. Техническая реализация
1. Зависимости (версии зафиксировать в `libs.versions.toml`):
   - `androidx.camera:camera-camera2`, `camera-lifecycle`, `camera-view`
     (CameraX, ~1.3.x);
   - `com.google.mlkit:barcode-scanning` (~17.x).
   Альтернатива — ZXing (`com.journeyapps:zxing-android-embedded`), проще
   интеграция, но старше и тяжелее. **Рекомендация: ML Kit + CameraX.**
2. Новый экран `ScanQrScreen` (route `scan_qr`): превью CameraX + анализатор
   ML Kit (`ImageAnalysis` + `BarcodeScanning.getClient`), фильтр типов —
   только QR.
3. `AndroidManifest`: разрешение `CAMERA`. Важно: сейчас приложение камеру
   **не запрашивает** (захват идёт по сети, RTSP), поэтому нужен runtime-
   запрос перед открытием `ScanQrScreen` + обработка отказа.
4. `AddCameraScreen`: кнопка со значком QR рядом с полем RTSP URL →
   навигация на `scan_qr`; результат возвращается через
   `savedStateHandle`/navigation result и заполняет поля.
5. Безопасность: содержимое QR содержит пароль — в логах не печатать,
   в UI показывать через `RtspUrlMasker`.

### 3.3. Проверка
- Ручная: сгенерировать два тестовых QR (строка и JSON), отсканировать,
  проверить автозаполнение и сохранение. **Требует устройства.**

## 4. Этап C — просмотр потока в детальном экране

### 4.1. Ограничение, влияющее на архитектуру
`media3-exoplayer-rtsp` жёстко требует `fmtp` (sprop-parameter-sets) в SDP
и падает на дешёвых камерах/NVR (см. комментарий в `RtspFrameCapture.kt`) —
именно поэтому захват кадров в своё время ушёл на FFmpeg. Поэтому «живой
просмотр» через ExoPlayer будет работать не на всех камерах пользователя.

### 4.2. Рекомендуемое решение: непрерывный FFmpeg-сеанс с прореживанием
Один долгоживущий сеанс FFmpegKit на время просмотра:
```
-y -rtsp_transport tcp -skip_frame nokey -i <url>
   -vf "select='not(mod(n\,N))'" -vsync vfr
   -q:v 3 -update 1 -f image2 <cache>/live.jpg
```
- `select='not(mod(n\,N))'` — на выход идёт каждый N-й кадр (N = настройка
  «Frame skip», по умолчанию 5);
- `-skip_frame nokey` — декoder сам выбрасывает не-ключевые кадры до декодирования
  (экономия CPU); при желании «каждый 5-й» считать по keyframe-потоку;
- `-update 1` — файл `live.jpg` постоянно перезаписывается (один файл,
  без засорения диска); атомарность не критична для превью;
- UI: `AsyncImage` с ключом = timestamp/счётчик, опрос файла раз в ~500 мс
  (`LaunchedEffect` + `delay`), показывается последний декодированный кадр;
- остановка: `FFmpegKit.cancel(sessionId)` в `DisposableEffect` (уход с
  экрана/пауза). Сеанс живёт, только пока открыт детальный экран.

Новый класс: `rtsp/RtspLiveViewer.kt` (`start(url, frameSkip)`, `stop()`,
Flow/cброс пути к актуальному файлу). Кадр в кэш (не в files), после остановки
удаляется.

Плюсы: одна RTSP-сессия, непрерывное декодирование, реальный «каждый 5-й кадр»,
работает с теми же камерами, что и snapshot (тот же FFmpeg).
Минусы: CPU/батарея во время просмотра (приемлемо — просмотр явный и
ограниченный по времени), задержка ~1–2 с.

### 4.3. Опциональный режим ExoPlayer (не в минимуме)
Настройка «Режим живого просмотра: FFmpeg (совместимый) / ExoPlayer (быстрый)».
ExoPlayer даст плавное видео без прореживания, но только на камерах с
корректным SDP. Включать вторым этапом, если потребуется.

### 4.4. Настройки (DataStore)
- `LIVE_FRAME_SKIP_KEY` (int, 1..20, по умолчанию 5).

### 4.5. Проверка
- Ручная на устройстве: открыть детали, убедиться, что кадры идут с
  ожидаемым прореживанием; уйти с экрана — сеанс FFmpeg завершён (по logcat),
  файл live.jpg удалён.

## 5. Общие замечания

1. **Устройство**: все три фичи проверяются только на реальном устройстве
   (QR — камера устройства; live view — сеть + камера). До этого — только
   сборка и unit-тесты логики.
2. **Миграция 1→2**: перед установкой новой версии на устройство с данными
   v1 убедиться, что миграция отработала (иначе URL будут потеряны — это
   единственный необратимый шаг этапа 2). Рекомендуется: установить, открыть,
   проверить, что камеры обновляются (значит URL переехали в Keystore-хранилище).
3. Worker остаётся без retry (одна попытка) — решение из блока 5 не меняется.
