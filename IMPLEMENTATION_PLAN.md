## 1. Текущее состояние проекта

  DataStore, Media3 1.11.0, WorkManager, Coil, Gson, Coroutines.

| Область | Состояние |

### 1.3. Что сломано / не сделано (критично)
1. **Сборка падает**: `assembleDebug` → «Cannot add extension with name 'kotlin'».
   Конфликт AGP 9.x (встроенный Kotlin) и плагина `org.jetbrains.kotlin.android`,
   плюс `composeOptions.kotlinCompilerExtensionVersion = 1.5.15` несовместим с Kotlin 2.x
   (нужен плагин `org.jetbrains.kotlin.plugin.compose`).
2. **Код рассогласован с моделью**: экраны и ViewModel используют поля
   `lastFramePath`, `isConnected`, `lastUpdateTime`, `location`, которых нет в `Camera`.
3. `CameraUpdateWorker` импортирует `dagger.hilt.*` — Hilt удалён, файл не компилируется.
4. Экраны импортируют `androidx.hilt.navigation.compose.hiltViewModel` — зависимость удалена.
5. `CameraDao.getCameraById(id: Int)` при `Camera.id: String` — рассинхрон типов.
6. **Нет безопасного хранения credentials**: RTSP URL с паролями хранятся в Room в открытом виде (нарушение ТЗ §16).
7. **Нет хранения кадров** по схеме `files/cameras/{cameraId}/latest.jpg` с атомарной заменой; сейчас кадр пишется во временный файл в cacheDir и не переживает очистку кэша.
8. **Нет планировщика**: очередь, concurrency limit (2), timeout (8–10 с), retry с backoff — ничего нет; `refreshAllCameras()` — последовательный цикл в ViewModel.
9. **Нет Live View** (полноценный Media3-плеер на экране камеры).
10. **Нет настроек как подсистемы**: DataStore-ключи размазаны по ViewModel; нет ночного режима, mobile data, темы, background refresh.
11. **Нет**: QR, импорт M3U, EditCameraScreen, меню камеры, сортировка, вкл/выкл камеры, empty state по ТЗ, диагностики.
12. **Нет тестов** (только заглушки ExampleUnitTest/ExampleInstrumentedTest).
13. **Нет маскировки URL в логах** — риск утечки паролей в Logcat (ТЗ §43).
14. В `DEVELOPMENT_LOG.md` в открытом виде лежат реальные логины/пароли RTSP —
    **удалить из файла и ротировать пароли**. В исходниках и логах паролей быть не должно.
15. Мусор в корне: `copy_project_script.py`, `save_progress.bat`.
16. Все изменения не закоммичены — риск потери работы.

### 1.4. Вывод
Проект прошёл этапы 1–2 из ТЗ §53 частично: анализ выполнен, POC написан, но
**не проверен на реальном потоке**, а текущее рабочее дерево не компилируется.
Дальнейшее движение без починки сборки и согласования модели бессмысленно.

## 2. Стратегия

Идём строго итерациями (ТЗ §53). Каждый этап ниже — **самостоятельное задание для LLM**
со своими критериями приёмки. Этапы выполняются по порядку; каждый следующий
опирается на результат предыдущего.

Обязательные правила для каждого задания (вставлять в промпт LLM):
- Работать в ветке `ai/<этап>` или текущей `ai/compose-mvp`; не трогать `main`.
- Перед изменениями: `git status`, `git diff`. Маленькие атомарные коммиты.
- После этапа: список изменённых файлов, `.\gradlew.bat assembleDebug`,
  `.\gradlew.bat testDebugUnitTest`, отчёт о результате.
- Не переписывать работающий код без необходимости.
- Никогда не логировать пароли; URL в логах маскировать: `rtsp://user:****@host:554/...`.
- Не хранить реальные credentials в исходниках, логах, документации.

### ЭТАП 1. RTSP proof-of-concept на реальной камере (самый рискованный)
**Цель:** доказано, что Media3 стабильно отдаёт один кадр из RTSP.

Задание LLM:
1. Доработать `RtspFrameCapture`:
   - корректное ожидание первого декодированного кадра (рассмотреть
     `VideoFrameMetadataListener` / `setVideoTextureView` + `PixelCopy`);
   - жёсткий timeout 8–10 с; гарантированное `player.release()` в finally;
   - никаких утечек Surface/декодера.
2. Сделать отладочный путь проверки (debug-экран или instrumented-тест),
   куда URL вводится вручную (не зашивать в код!).
3. Прогнать минимум на 2 реальных камерах пользователя (URL даёт пользователь,
   в код/логи не писать). Зафиксировать: время до первого кадра, стабильность
   10 попыток подряд, поведение при недоступной камере.
4. Если Media3 нестабилен — сравнить с альтернативами (LibVLC, FFmpegKit и т.п.)
   по ТЗ §28/§56 и выдать письменное заключение до продолжения.

**Приёмка:** 10/10 успешных захватов на доступной камере; при недоступной —
быстрый fail по timeout без зависаний и утечек; отчёт с цифрами.

### ЭТАП 2. Модель данных, Room, безопасное хранение
**Цель:** правильное разделение metadata / secret / runtime state / cached frame.

Задание LLM:
1. Разделить сущности:
   - `CameraEntity` (Room): id, name, urlReference (ключ к секрету), enabled,
     createdAt, sortOrder, lastSuccessfulFrameAt, lastAttemptAt, lastError,
     consecutiveErrors;
   - секреты (RTSP URL с credentials) — в EncryptedSharedPreferences
     (AndroidX Security / Keystore) под ключом = urlReference;
   - runtime-статус (`CameraStatus`) — не хранить в Room, вычислять/держать в памяти.
2. Миграция БД v1 → v2 (БД ещё не в продакшене — допустимо fallbackToDestructiveMigration,
   но решение зафиксировать).
3. Утилиты `RtspUrlParser` (корректный разбор `user:pass@host`, URL encoding,
   query params) и `RtspUrlMasker` (`rtsp://user:****@host:554/...`) —
   маскер использовать во всех логах.
4. Репозиторий: CRUD + Flow списка камер; при выдаче наружу URL собирается
   из секрета, в логах/исключениях — только маскированный.

**Приёмка:** unit-тесты на парсер и маскер (включая случаи из ТЗ §46–47)
проходят; в дампе Room нет паролей; `assembleDebug` SUCCESS.

### ЭТАП 3. Snapshot engine
**Цель:** надёжный `RtspFrameCapture` как отдельный компонент вне UI.

Задание LLM:
1. Контракт: `suspend fun captureFrame(cameraId, rtspUrl): Result<Frame>`.
2. Хранение кадра: `files/cameras/{cameraId}/latest.jpg`, атомарная замена
   (запись во временный + rename), JPEG 75–85%, масштаб до ~640px по большей
   стороне с сохранением aspect ratio.
3. Timeout, отмена, гарантированное освобождение ресурсов; после успеха —
   обновить `lastSuccessfulFrameAt`, при ошибке — `lastAttemptAt`,
   `lastError`, `consecutiveErrors` (старый кадр НЕ трогать).
4. Очистка файлов при удалении камеры.

**Приёмка:** ручная проверка: кадр сохраняется, переживает перезапуск приложения,
старый кадр остаётся при неудаче; unit-тест на логику обновления счётчиков/статусов.

### ЭТАП 5. Планировщик обновления
**Цель:** очередь обновления по ТЗ §7, §29–31.

Задание LLM:
1. `CameraRefreshScheduler`: очередь задач, concurrency = 2 (настраиваемая
   константа), per-camera timeout, retry ≤ 2 с backoff, без бесконечных циклов.
2. Периодика: 10/20/30/60 с, 5 мин, отключено; по умолчанию 20 с;
   чтение интервала из DataStore.
3. Lifecycle-aware: работает пока приложение видимо, останавливается в фоне
   (до включения background refresh в этапе 8).
4. Зависшая камера не блокирует очередь (timeout принудительно закрывает player).

**Приёмка:** на 5 камерах видно последовательное обновление не более 2
одновременно; лог (маскированный) показывает очередь; при обрыве сети —
переход в OFFLINE без бесконечных попыток.

## 4. Порядок и зависимости этапов

```
ЭТАП 0 (сборка) → ЭТАП 1 (RTSP POC) → ЭТАП 2 (данные/секреты) →
ЭТАП 3 (snapshot) → ЭТАП 4 (стена) → ЭТАП 5 (планировщик) →

ЭТАП 9 (M3U/QR) → ЭТАП 10 (тесты/диагностика) → ЭТАП 11 (оптимизация)
```

MVP = этапы 0–8 (ТЗ §52). Этапы 9–11 — после стабильного MVP.

## 5. Риски
1. **Media3 snapshot** — главный технический риск; закрывается этапом 1 до
   написания остального кода.
2. **AGP 9.3.1** — свежий инструмент; если этап 0 не решит конфликт чисто,
   понизить до стабильной 8.x.
3. **Фоновые ограничения Android** — не обещать 20 с в фоне; только WorkManager ≥ 15 мин.
4. **Утечка credentials** — маскировка логов обязательна с этапа 2; пароли из
   DEVELOPMENT_LOG.md удалить и ротировать немедленно.
