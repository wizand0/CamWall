## 0. ВАЖНО: план v2 описывает архитектуру, которая не была реализована

v2 предполагал чинить захват через `ExoPlayer + ImageReader` (media3, RGBA_8888,
`RtspMediaSource.setForceUseRtpTcp(true)`). Эта версия была написана и собрана, но
уперлась в неустранимый (на стороне androidx.media3) баг:

```
java.lang.IllegalArgumentException: missing attribute fmtp
    at RtspMediaTrack.generatePayloadFormat
```

Причина: камера пользователя отдаёт **HEVC (H.265)**, а не H.264, как неявно
предполагалось в v1/v2. SDP-ответ камеры (HIK Media Server V4.51.006) не содержит
атрибут `fmtp` для видео-трека — `androidx.media3:media3-exoplayer-rtsp` жёстко
требует его и падает ещё до старта воспроизведения. Это подтверждённый открытый
баг апстрима (github.com/androidx/media issues #901, #1456, #2208), фикса нет.

**Решение — полная замена движка захвата на FFmpeg**, как и VLC на десктопе,
он не требует `fmtp` и достаёт параметры кодека прямо из потока.

### Что изменилось технически
- `RtspFrameCapture.kt` переписан с нуля: вместо ExoPlayer/ImageReader использует
  `FFmpegKit.executeWithArgumentsAsync(...)`.
- Зависимость: `com.moizhassan.ffmpeg:ffmpeg-kit-16kb:6.1.1` — активно
  поддерживаемый форк архивированного 02.07.2026 `arthenica/ffmpeg-kit`,
  тот же Java API, публикуется на Maven Central.
- Команда захвата:
  ```
  ffmpeg -y -rtsp_transport tcp -timeout <us> -skip_frame nokey \
    -i <rtspUrl> -frames:v 3 -q:v 2 -vf "scale='min(640,iw)':-2" \
    -f image2 burst_tmp/frame_%03d.jpg
  ```
  - `-skip_frame nokey` (обязательно **до** `-i`, иначе трактуется как опция
    энкодера вывода и падает с ошибкой) — декодер пропускает все не-ключевые
    кадры, гарантируя, что каждый выданный кадр самодостаточен (не зависит от
    предыдущих). Без этого первый пришедший кадр после подключения может быть
    P-кадром без нужного опорного кадра → декодер выдаёт битую/серую картинку
    (`Could not find ref with POC N`).
  - Берутся **3 кадра подряд** (`WARMUP_FRAMES`), используется последний —
    подстраховка на случай, если первый keyframe после reconnect менее
    стабилен по экспозиции/фокусу у конкретной камеры. Стоимость: +2-4 сек на
    каждое обновление (интервал keyframe у камеры ~1-2 сек).
  - `-f mjpeg`/`-f image2` указывается явно, т.к. временный файл не может иметь
    расширение `.jpg` до финального rename (иначе `Unable to find a suitable
    output format`).
- Атомарная запись (tmp + rename) сохранена как в v1/v2 (ТЗ §8).
- `media3-exoplayer`, `media3-extractor`, `media3-datasource`,
  `media3-exoplayer-rtsp` **больше не нужны** для захвата — оставлены только
  `media3-common`/`media3-ui`, если понадобятся для Live View (этап 6).

### Подтверждено логами (несколько прогонов, разные камеры/каналы)

## 2. Текущий главный дефект: автообновление не работает (оба механизма)

Пользователь подтвердил: не работает ни плановое фоновое обновление, ни
обновление при открытии экрана камер.

### 2.1. Обновление при открытии CameraWallScreen ("быстрый старт")
По коду `CameraWallScreen.kt` (уже видел в этой сессии) — **это не баг, а
нереализованная фича**. `LaunchedEffect(Unit)` на экране стены вызывает только:
```kotlin
viewModel.loadCameras()
```
Обновления камер без кадра (`lastSuccessfulFrameAt == null`) там нет вообще.
Нужно реализовать — см. §3.1 ниже.

### 2.2. Плановое фоновое обновление (WorkManager)
`CameraWallViewModel` содержит методы `scheduleCameraUpdates(intervalMinutes)`,
`cancelCameraUpdates()`, `triggerOneTimeUpdate()`, использующие
`CameraUpdateManager(application)`. **Файлы `CameraUpdateManager.kt` и
`CameraUpdateWorker.kt` (или как называется Worker) ещё не показаны в этой
сессии** — нужны для диагностики. Вероятные причины по опыту с WorkManager:
- `scheduleCameraUpdates(...)` никогда не вызывается из UI (нет экрана/тумблера,
  который бы это включал — в `CameraWallScreen`/`SettingsScreen` вызовов не видно).
- Периодичность настроена, но `WorkRequest` не имеет корректных `Constraints`
  (например, требует `NetworkType.CONNECTED`, а устройство считает сеть
  недоступной из-за Doze/battery optimization).
- `CameraUpdateWorker.doWork()` может сам зависеть от старого/сломанного
  `RtspFrameCapture` — если Worker не был обновлён вместе с переходом на
  FFmpeg, там всё ещё старый вызов, который теперь не соответствует новой
  сигнатуре или не подключён к DI/Factory так же, как во ViewModel.
- WorkManager при сборке `assembleDebug` создаёт по умолчанию, но если
  `Application` не наследует `Configuration.Provider` (лог из более раннего
  прогона показывал `WM-WrkMgrInitializer: Initializing WorkManager with
  default configuration` — то есть initializer сработал сам, это нормально,
  но не гарантирует, что задачи реально ставятся в очередь).

## 5. Важное предупреждение на будущее (этап 6, Live View)

Этап 6 планирует Media3-плеер для живого просмотра в `CameraDetailScreen`.
**Media3 RTSP уже показал несовместимость с этой камерой** (баг с `fmtp` на
HEVC). Снапшоты мы решили через FFmpeg, но живое воспроизведение через
`media3-exoplayer-rtsp` **скорее всего упрётся в ту же ошибку** — это нужно
перепроверить отдельно перед началом работы над этапом 6, а не предполагать,
что раз снапшоты работают, то и live-плеер заработает. Если баг подтвердится
и там — вариантами будут: (а) FFmpeg-транскодинг RTSP→HLS локально и
проигрывание HLS через media3 (сложнее, but media3 отлично работает с HLS),
(б) полный переход на libVLC для live-плеера тоже, (в) MediaCodec напрямую.
